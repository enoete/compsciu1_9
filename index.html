The method: six steps, in order

Every piece of software you have ever used went through these six. Skip one — especially the first — and you build something beautiful that solves the wrong problem.

Nobody builds a house by starting with the roof

You agree what the house is for. You survey the land. You look at a few designs. You pick one you can afford. You build it. Then somebody inspects it before anyone moves in. Software is the same six moves, and the expensive mistakes happen in exactly the same place: a house built from a vague brief is still a house, just not the one anybody wanted.

Spot the ambiguity

An algorithm must have only one possible interpretation. Each instruction below is ambiguous. Click the word or phrase that a computer could not act on.

Cohesion — high is good

Each module does one job well. A module called calculateTax that also prints receipts and emails the customer has low cohesion, and you will regret it.

Coupling — low is good

Modules should depend on each other as little as possible. High coupling means changing one thing breaks three others. Remember it as: high cohesion, low coupling.

What makes it an algorithm

Four properties. Miss any one and what you have written is a suggestion, not an algorithm.

Precise

Exact instructions. "Add 15% tax", not "add some tax".

Unambiguous

Only one possible reading. No "a bit", no "soon", no "the good one".

Finite

It stops. A loop with no exit is not an algorithm, it is a hang.

Logical sequence

Steps in an order that makes sense. You cannot serve the tea before boiling the water.

The four sections every written algorithm needs. Header (its name) → Variable declaration (what it will use) → Program body (the steps) → Terminator (an end statement). Markers look for all four. Losing a mark for a missing STOP is the cheapest mark you will ever throw away.

The symbols

Shapes are a language, not decoration

A diamond does not mean "important step". It means a question with exactly two ways out. If your diamond has one arrow leaving it, it should have been a rectangle. If your rectangle has two, it should have been a diamond. That single rule catches most flowchart mistakes before a marker does.

Choices and loops

Three building blocks make every program ever written: do things in order, choose between things, repeat things. You have the first one already. Here are the other two.

Which loop? Ask one question

Do I know how many times before I start? If yes — ten items, five students, four bits — use a FOR loop. If no — until the user types -1, until the password is right, until the queue is empty — use a WHILE. And if the thing must happen at least once before you can even test the condition, like asking for a password, that is REPEAT UNTIL.

Loop lab

The same job written three ways. Run each and watch the counter — then look at what happens when the input makes the loop body run zero times.

OUTPUT

The zero-iteration trap. A WHILE loop can run no times at all if its condition starts false. A REPEAT UNTIL always runs at least once, because it tests at the bottom. Exams love this difference — switch the loop lab to the WHILE version and set the count to 0 to watch it happen.

Trace tables

The single most examined skill in this topic, and the one most people lose marks on. A trace table shows every variable's value after every step. Do it slowly and you cannot get it wrong.

You are the computer now, and you are very stupid

That is the whole trick. Do not look at the algorithm and work out what it means. Take one line at a time, do exactly what it says, write down what changed, move to the next line. The moment you start skipping ahead because you "can see where this is going", you make the mistake the question was built to catch.

The four rules

  1. One column per variable, plus a column for output. Set them up before you start.
  2. One row per change. If a line does not change anything, it does not need a row.
  3. Carry values across. A variable keeps its value until something changes it — do not leave gaps.
  4. Loops repeat rows. Go round as many times as the loop does, writing a new row each pass. This is where it gets long, and where people start guessing.

Requirements

Before anyone writes a line of code, somebody has to say what the system must do and how well it must do it. Those are two different lists, and mixing them up is a guaranteed lost mark.

Ordering food

"I want a chicken roti" is functional — it is the thing itself. "I want it in under fifteen minutes, still hot, and not swimming in pepper" is non-functional — it is how well the thing is delivered. Both matter. You would send back a cold roti that arrived in an hour, even though it was technically the right order.

Drag each requirement into the right bin. Some are trickier than they look.

The one-second test. Does the sentence describe a thing the system does — create, search, calculate, display, send? Functional. Does it describe how well — fast, secure, reliable, available, easy, works-on-X? Non-functional. Verbs versus adjectives.
